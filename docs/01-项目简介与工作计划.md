# 一、项目简介

## 1.1 外行版（约 350 字，给完全不懂技术的评委、领导或家人看）

**一句话：它是个"网页体检工具"——用 AI 帮你写完网页之后，用它查一查这网页在别人的浏览器里会不会打不开，并告诉你怎么改。**

现在很多人让 AI 帮忙写网页。AI 写得飞快，但有个坑：同一段代码，在新版浏览器里一切正常，到了旧一点的浏览器里可能整页空白。问 AI"这能跑吗"，它常常会一本正经地编一个答案 —— 就像有人不看说明书就告诉你"这药一天吃两次"，听着专业，其实没查过。

CompatAI 的做法很朴素：**先查说明书，再让 AI 解释。**

它自带一本"浏览器兼容字典"，收录一万三千多条功能的支持情况（数据来自浏览器厂商公开维护的权威资料）。代码写完，它逐条对照：这个功能 Safari 从哪个版本才支持，写得清清楚楚。**字典说不支持，就是不支持，AI 没有投票权。**

查完字典，AI 才出场，负责把"为什么不行、该怎么改"讲成人话，并给出具体改法。如果 AI 说的版本号和字典对不上，系统会当场拦下让它重写；实在改不对，就老实说"这条需要人工确认"，而不是硬编一个答案。

最后还要"验收"：把改过的代码重新检测一遍，再放进隔离的测试环境里真跑一次，看问题是不是真解决了、有没有顺手弄坏其他地方。

它还有两个好处：**全部在你自己的电脑上运行**，不联网、不上传代码；同一个输入，**每次给出的结论都一模一样**。

> 如果只讲三句话：AI 写的网页不一定能在别人的浏览器里跑；我们不问 AI、只查权威资料来判定；AI 只能负责解释和给改法，改完还要重新检查一遍。

## 1.2 简短版（约 400 字，可直接用于摘要、申报表、汇报开场）

**CompatAI** 是一个面向 AI 辅助编码时代的浏览器兼容性检测与验证系统。

它要解决的问题是：大模型让代码产出变快了，但"这段代码在 Safari 14.1 能不能跑"这个问题反而更难回答
—— 直接问模型会得到两种失败：**给出看似精确却错误的版本号**（幻觉），以及**同一段代码两次询问结论不一致**（不可复现）。

CompatAI 的方案是把"判定"和"解释"彻底切开，分成三层：**L1** 用解析器 + 本地 MDN BCD 索引（13,196 条特性、16 个浏览器）
做纯查表判定，无网络、无大模型，是唯一有权说"不支持"的组件；**L2** 让大模型只负责把结论翻译成人话并给出等价修复，
并用四道闸门（输入白名单、结构化输出、后置校验、确定性降级）拦住幻觉；**L3** 把修复后的代码重新回灌 L1，
并用 jsdom 沙箱对比执行期行为与 DOM 结构，验证修复是否真的有效。

核心主张一句话：**大模型可以参与"怎么解释"，但不能参与"哪些浏览器不支持"。**
系统 100% 离线可运行（BCD 数据、前端依赖、图表库全部本地化），150 项后端测试全部通过，
同一输入两次调用响应逐字节相同，断网环境下仍可完整演示三层链路。

## 1.3 一句话版本（用于标题、海报、PPT 封面副标题）

> 用「确定性查表」判定兼容性、用「受约束的大模型」解释与修复、用「沙箱回灌」验证修复 —— 让兼容性结论从"模型的表达"变回"可追溯的事实"。

## 1.4 详细版（约 2,000 字）

### （1）问题：AI 擅长生成，不擅长验证

在 AI 辅助编码普及之后，浏览器兼容性问题的形态变了。代码产出的速度大幅提升，
但**兼容性判断的依据并没有随之变得可靠**。把源码直接丢给大模型问"这段代码在 Safari 14.1 能跑吗"，
会得到两类典型失败：

- **幻觉**：模型给出看似精确、实则错误的版本号。例如声称"Safari 15 起支持"，而真实门槛是 15.4；
  差的这 0.4 个版本，足以让一份在 15.0 上必崩的代码被判定为"安全"。
- **不可复现**：同一段代码两次询问，结论不一致；换一个模型，结论又变一次。

对课程作业而言，这只是"说法不严谨"；但对结题报告与真实工程而言，这是缺陷。
**兼容性结论必须是可追溯、可复现的事实，而不是模型的表达。**

### （2）思路：把"判定"与"解释"切成三层，各层只做一件事

| 层 | 做什么 | 谁来做 | 能否产生"事实" |
|---|---|---|---|
| **L1 判定** | 从源码提取 Web 特性，逐条查询 MDN BCD | 解析器 + 本地索引，无网络、无大模型 | ✅ 唯一事实来源 |
| **L2 解释** | 把 L1 的结论翻译成自然语言，给出等价修复 | 大模型，但被四道闸门约束 | ❌ 只解释，不判定 |
| **L3 验证** | 把修复后的代码回灌 L1，并用 jsdom 对比行为 | 确定性代码 + 沙箱 | ✅ 可验证的结论 |

这个划分的价值在于**可审计、可复现、可替换**：每条问题都带 `bcd_path` 与 `source_data`，能一路追到 MDN 原始数据；
L1 没有任何随机性；L2 换模型、换供应商甚至整个关掉，L1 与 L3 完全不受影响。

### （3）关键能力

**L1 · 三维确定性静态检测。** CSS 用 `tinycss2` 解析，并**结合同规则块的 `display` 值推断布局上下文**
—— 这一点直接决定正确性：`gap` 在 BCD 里是上下文相关的，基础路径 `css.properties.gap` 的 Safari 门槛是 10.1，
而 Flex 布局的真实门槛在子路径 `gap.flex_context`（Safari 14.1）。只查基础路径会**过于乐观**，把 Safari 12 误判为支持。
JS 采用 `esprima` AST + **自写 tokenizer 双通道**：esprima 停在 ES2018 附近，遇到 `obj?.name` 会直接抛语法错误，
若只用 AST，一份用了可选链的文件会**整份失去检测**；因此 tokenizer 常驻负责语法级特性，AST 负责 API 级特性，
解析失败时退回 token 链扫描兜底。HTML 用 `BeautifulSoup4` 的 `html.parser`（唯一提供 `sourceline` 的内置解析器），
并把内嵌的 `<style>` / `<script>` / `style=""` 交给对应解析器，行号按内嵌位置平移。

**L2 · 防幻觉的四道闸门。** ① 输入白名单：Prompt 只含 L1 命中的 issue 与命中行 ±20 行上下文，
模型没有"自由发挥"的素材；② 结构化输出：`json_schema` 中用 `enum` 把 `issue_id` 枚举死，不支持时依次降级；
③ 后置校验：版本号封闭（依据写 15.4、解释写 15 即拦）、口径检查（语法级问题必须谈"解析阶段失败"，
API 级必须谈"成员不存在"）、修复代码语法门禁（`tinycss2` / 括号配平 / 标签闭合）；
④ 确定性降级：重试仍失败则走模板化解释，标记 `degraded=true`、`needs_human=true`、不给修复代码。
**宁可说"未知"，也不给编造的答案。**

**L3 · 沙箱验证。** 回灌重检按 `(type, bcd_path, feature)` 三元组比对，刻意不含行号与 id（修复会让行号整体位移）；
修复以「行区间替换」表达，合成时按行号倒序应用，**N 条修复可叠加成一次修复**（实测 11 条全部合并、问题归零）。
jsdom 执行原始与修复后代码，比较执行期异常与 DOM 结构变化。用户代码里的 `while (true) {}` 是同步阻塞，
`setTimeout` 永远不会触发，因此采用 **worker_threads 到点 `terminate()`** + Python 侧 `taskkill /F /T` 杀进程树的
两层超时机制，超时返回结构化错误而**不拖死请求线程**。

**前端 · 100% 离线。** 深色侧边栏 + 卡片式 Dashboard，设计 token 集中于 `assets/tokens.css`；
Tailwind 3.4.16 与 ECharts 5.5.1 全部本地化至 `assets/vendor/`，页面无任何 `https://` 外链，
已在 Chrome `--host-resolver-rules` 断网下实测可用。

### （5）应用价值与适用边界

**价值。** 对个人与团队，它是一个能塞进本地开发流程的"兼容性体检工具"，不联网、不上传代码；
对 AI 编码工具链，它示范了一种可复用的架构范式 —— **把不可靠的生成能力，包在可靠的判定与验证之间**；
对教学，它把"防幻觉"从一句口号变成了四道可以逐条演示、逐条拦截的工程闸门。

**边界（刻意写清楚）。** 系统不做 CSS 值级分析（`position: sticky` 只查属性级门槛）；
前缀敏感条目按 BCD 如实反映，不猜前缀；jsdom 没有布局引擎，**验证不了视觉差异**；
"已解决"可能只是"查不到"，因此单列 `needs_review` 交由人工复核。
系统的价值取决于结论可信，而可信的前提是知道哪里不可信。
